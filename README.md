技术本身我是真喜欢，但广告这行更让我上心的是它前面那截：谁在买、谁在卖、一次曝光怎么在几十毫秒里成交，钱又是沿着哪条路分下去的。工程只是这条因果链的中段，只盯着中段，很多决定会看不出道理。

我的日常是 DSP 竞价。OpenRTB 请求进来，出价出去，中间卡着一个不讲情面的 `tmax`。往上要弄清协议、拍卖规则、SDK 与合规，往下要扛住定向、频控、pacing、打分，再往后是 Kafka、Flink 和在线推理。哪一段还含糊，我就把它拆开写一遍，写到能跟人讲明白为止——生意上的说法和延迟预算对不上的时候，通常是我还没真懂。

写下来的东西都放在 **[cylshao.com](https://cylshao.com)**，到现在大约 160 篇。

## 工作

- **Bidder**：协议解析 → 定向 → 召回 → 打分 → 出价。先把延迟预算沿着这条链路切清楚，每段花多少毫秒心里有数，再谈各自怎么优化。
- **投放控制**：频控、预算 pacing，以及 campaign 配置怎么编译进线上、改完之后怎么全量或增量发出去。
- **推理服务**：把 CTR / CVR 打分从竞价进程里拆出来做成独立的高并发服务，让模型的迭代节奏和竞价的稳定性各走各的。

## 最近在看

这两年我把更多时间花在了 AI Agent 上。

差别其实不在模型聪不聪明。聊天能给你一份步骤，但一步都不会替你做；要真把事办完，它得自己调工具、把中间状态保住、在需要人点头的地方停下来，等人回了话再接着往下跑。

放进企业里，卡住的也基本是这几层，而不是模型本身：哪些工具敢交给它、上下文怎么收才不至于越滚越长、出错时在哪一步停、中断之后从哪儿续、这一趟到底花了多少钱。这些问题和我熟悉的那套东西其实同构——超时预算、幂等、重试、审计，只是换了个场景重新出现一遍。所以我认为它会是模型真正进入日常工作的那一层，也值得认真做。

我的做法是先不套框架，自己把循环拆开写一遍，工具、记忆、评测、成本、续跑各写一层，再回头对照 LangGraph 这类运行时，看它把哪些层收进了自己的抽象里。

## 写作

上面这些大多写成了文章，落在四个方向上，问的是同一件事：流量怎么变成收入，系统在中间怎么跑。

| 方向 | 在写什么 |
| :--- | :--- |
| 广告 | OpenRTB、Header Bidding、App SDK、RTA、合规与归因 |
| 基建 | Netty、Kafka、Flink、Redis、高可用、Kubernetes |
| 模型 | 特征、召回 → 精排 → 重排、在线推理 |
| Agent | 循环、工具、记忆、评测、续跑，以及框架怎么对应这几层 |

每篇都自己画图，也会把当时为什么这么选、放弃了什么一并写出来。不写软文。
